# Decision log

| Date | Decision | Why | Alternatives considered |
| --- | --- | --- | --- |
| 2026-10-27 | Use NEMWEB daily archives, falling back to 5-minute "Current" files for the last day or two | Daily archives are one download per day and keep about 13 months | Monthly MMSDM archives (very large files, a month behind) |
| 2026-10-27 | Store in DuckDB | Single file, no server, fast analytics, works the same on Windows and Linux | SQLite (slow for analytics), PostgreSQL (needs a server) |
| 2026-10-27 | Keep AEMO market time (AEST) and interval-ending timestamps | Matches every AEMO dataset and avoids daylight-saving gaps | Converting to local time or UTC |
| 2026-10-27 | Validate with pandera and quarantine failing rows | Declarative schemas, readable failure reasons, nothing lost | Dropping bad rows, failing whole files |
| 2026-10-27 | Batch all 288 five-minute files in a daily archive before validating | One validation and one upsert per day instead of 288 | Per-file processing (about 50 times slower in tests) |
| 2026-10-27 | Region balance tolerance 50 MW and SCADA tolerance 150 MW, provisional | Starting values only; to be tuned from the residual distribution on real data | None yet. Revisit after the first real week |
| 2026-10-27 | Keep interventions out (INTERVENTION = 0 only) | Intervention runs are what-if pricing runs, not physical dispatch | Storing both with a flag |
| 2026-10-27 | Tighten the region balance tolerance from 50 MW to 1 MW | First real week (19 to 25 Oct 2026, 2,016 SA intervals): mean residual 0.00 MW, 95th percentile absolute residual 0.01 MW. The identity holds exactly, which also confirms NETINTERCHANGE is net export. Because it holds by construction it is a consistency check on parsing and typing, not an independent check; the SCADA comparison is the independent one | Keeping 50 MW (would hide real parsing errors of up to 50 MW) |
| 2026-10-27 | Add SA dispatch prices (DISPATCH_PRICE), with RRP valid from -1,000 to 25,000 $/MWh | Constraint and interconnector investigations need price to show cost. -1,000 is the market floor; the cap is 20,300 for 2025-26 and rises each July, so 25,000 allows for that while still catching a mis-scaled value | No upper bound (would let a units or parsing error through); exact current cap (would reject real prices after the next July increase) |
| 2026-10-27 | Add SA rooftop PV from AEMO's MEASUREMENT estimate only, keeping its half-hour start timestamp | Rooftop solar is not in dispatch data but drives SA's midday demand and prices. MEASUREMENT is built from metered systems (quality indicator 1); SATELLITE (0.6) gives a different value for the same half hour, so keeping both would double count | SATELLITE only; both with a TYPE filter left to every query; relabelling to interval-ending time (would hide AEMO's convention) |
| 2026-10-27 | Investigations compare conditions within the same hour of day, and resample whole days for confidence intervals | In SA, rooftop PV, demand, price and interconnector flow all follow the clock, so a raw difference mostly measures time of day. Intervals within a day are not independent | Raw differences with interval-level bootstrap (overstates certainty and confounds time of day) |
| 2026-10-27 | Treat marginal values of 100,000 or more as constraint violation penalties and report them separately | One constraint (VT_ZERO) averaged about -27 million in the first week and would swamp any average | Dropping them silently; capping them |
| 2026-10-27 | Take wind and solar farm output from SS_WIND_CLEAREDMW and SS_SOLAR_CLEAREDMW, plus their UIGF forecasts and battery (BDU) columns | AEMO publishes TOTALINTERMITTENTGENERATION as 0 in every SA interval of the first week; the semi-scheduled columns hold the real values (e.g. 79 MW wind and 158 MW solar at 13:00 on 21 Oct) and UIGF minus cleared shows curtailment | Summing unit SCADA by fuel (needs the registry and is metered, not dispatched) |
| 2026-10-27 | Columns AEMO added in later file versions are optional, and the store adds new columns to existing tables | Older archives must still load, and a database created by an earlier release must keep working after an upgrade | Failing files that lack a column; rebuilding the database |
| 2026-10-27 | Build the generator registry from NEMWEB's MMSDM registration tables by default | aemo.com.au blocks scripted access and was blocking browsers too; NEMWEB is the same AEMO source as the rest of the data, needs no manual step, and gives capacity and fuel per generating set, with history to pick the rows in force on a date | Manual download of the Excel registration list (kept as an option) |
| 2026-10-27 | Accept DUIDs containing `-`, `#` and `/` | 13 real units (OSB-AG in SA, TARONG#1, W/HOE#1 and others) were being rejected: 26,208 rows in the first week | Keeping the stricter pattern |
| 2026-10-27 | A reload replaces the file's rejects | After the DUID fix, a backfill loaded all 26,208 previously rejected rows, but the rejects table still held them and the reject rate stayed at 0.82%. Rejects should describe the data as stored now; each run's manifest keeps the history | Counting only rejects from the latest run (wrong when a run loads only some files) |
| 2026-10-27 | SCADA-vs-dispatch sums scheduled and semi-scheduled generators plus battery output (battery SCADA clipped at 0) | First real week: the gap was most negative in the evening (down to -624 MW), when batteries discharge. With battery output counted, the mean gap went from -56.7 MW to +14.0 MW, the 95th percentile of the absolute gap from 343.7 MW to 130.7 MW, and detected shifts from 51 to 3; in intervals with over 100 MW of battery discharge the mean gap is -0.5 MW. Leaving batteries out made a coverage gap look like a telemetry fault | Comparing generators only |
| 2026-10-27 | Registry rows in force: latest effective date first, then the highest version on that date; capacity from DUDETAIL at unit level | AEMO restarts VERSIONNO at 1 on each new effective date (OSB-AG: 2000 row version 39, 2024 row version 1), so taking both maxima separately matched no row for 298 units. DUDETAIL capacity agrees with the sum over generating sets (Pelican Point: 160 + 160 + 158 = 478 MW registered, 179 + 179 + 164 = 522 MW maximum) and is at the same level as SCADA | Highest version regardless of date; summing GENUNITS capacity |
| 2026-10-27 | Compare dispatched generation for interval t with SCADA stamped t + 5 minutes | On real data (21 Oct, 10 unit-interval checks) DISPATCH_UNIT_SCADA stamped t equals UNIT_SOLUTION.INITIALMW for t exactly, so it is the reading at the start of interval t. Comparing it with the target for t measures ramping, not telemetry (CGBESS01 at 18:30: -0.04 MW at t, 42.47 MW at t + 5, target 44 MW) | Comparing readings and targets with the same stamp |
| 2026-10-27 | Keep the SCADA-vs-dispatch tolerance at 150 MW and treat the +13 MW mean gap as known bias | After the battery and timing fixes (19 to 25 Oct): mean gap +13.5 MW, 95th percentile of the absolute gap 85.1 MW, no shifts detected, 15 intervals over 150 MW. On 21 Oct the summed unit targets (UNIT_SOLUTION TOTALCLEARED) equal DISPATCHABLEGENERATION exactly, and the gap is many units running slightly above target (wind farms +5.1 MW, batteries +4.9 MW in total), not a missing unit or meter fault | Tightening to 100 MW (would flag normal ramps) |
| 2026-10-27 | Judge I3 spikes and stuck values against each unit's dispatch target (Next Day Dispatch UNIT_SOLUTION) when loaded | First real week: 8 of the 10 units with the most "spikes" were batteries following dispatch (HPR1 moved from -29.7 to -59 MW on a -59 MW target), and Pelican Point's "stuck" runs sat at a steady low load. Readings alone can't tell these from telemetry faults; the target can | Excluding batteries from the spike check (would also hide real battery telemetry faults) |
| 2026-10-27 | Fetch Next Day Dispatch from Current first, by trading day | Current keeps about 13 months of ~8 MB daily files while the archive is one ~220 MB zip per month; a file for day D covers 04:05 on D to 04:00 on D+1, so day D also needs the D-1 file | Archive first, as for other reports |
| 2026-10-27 | A target-based spike must itself be off target by the threshold; semi-scheduled one-interval departures are "brief departures" (low severity) | First real week with targets: 17 flagged readings matched their own target while both neighbours were off it, so the rule flagged the one correct reading. Of 368 spikes, the most were at semi-scheduled solar and wind farms (BNGSF1 42, TBSF1 36), whose target is a forecast: one interval away from it is usually cloud or a gust | Dropping semi-scheduled units from the check (would hide real telemetry faults) |
| 2026-10-27 | Parse only the columns each dataset uses, and load in batches of about 50 MB of CSV | UNIT_SOLUTION has 69 columns and we use 8. A week of targets peaked at 1.3 GB on a Windows PC; on a synthetic trading day of the same shape, parsing only used columns cut peak memory from 688 MB to 246 MB, and reading lines without io.StringIO (which holds a second, wider copy of the text) to 150 MB | Keeping every column |
| 2026-10-27 | Report a scheduled unit 20 MW (or 10% of capacity) off target on the same side for 15 minutes or more as one "off target" episode, and skip spikes inside it | BUNGAMB1 on 20 Oct was told to charge at -100 MW for 25 minutes and swung between -10 and -69 MW; the alternating readings were flagged as two spikes. It is a battery not meeting its target (likely near full), a conformance question, not telemetry. The clear telemetry faults that week were SMFBESS1 reading -68 MW on a +68 MW target (a sign flip) and 119.5 MW while not offered | Keeping the spike rule alone |
