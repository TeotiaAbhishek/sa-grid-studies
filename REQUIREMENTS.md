# SA Grid Studies: Requirements and Acceptance Criteria

A portfolio project that automates data collection and repeatable power system studies for South Australia, using public data only.

## 1. Purpose

Engineers who run network studies need a reliable, traceable feed of real operating conditions, and they need a way to rerun studies the same way every time. This project builds both:

- **Stage 1 (pipeline):** automated, defensive ingest of AEMO NEMWEB data for the SA1 region, producing validated, analysis-ready tables.
- **Stage 2 (studies):** scripted N-1 contingency studies in pandapower, driven by real SA operating snapshots from Stage 1, with automated checks on the results.

**Out of scope:** forecasting, any non-public or ElectraNet data, and any claim that the study network models the real SA transmission system. The Stage 2 network is a published test case (see section 4).

## 2. Users and needs

| User | Need |
|---|---|
| Power system engineer | Pick real operating snapshots (such as peak demand or minimum demand) and run a study on them without hand-copying data |
| Analyst or manager | See demand, interconnector flows and binding constraints for SA in Power BI |
| Reviewer or auditor | Rerun any past study and get identical results, and see where every input came from |

## 3. Stage 1: NEMWEB pipeline

### Data sources (public, AEMO NEMWEB)
- `DISPATCHREGIONSUM`: SA1 demand, generation and rooftop PV (5-minute)
- `DISPATCHINTERCONNECTORRES`: flows on V-SA (Heywood) and V-S-MNSP1 (Murraylink)
- `DISPATCHCONSTRAINT`: binding network constraints and their marginal values
- `DISPATCH_UNIT_SCADA`: unit-level output for SA generators
- Generator registration list: maps each unit (DUID) to its region and fuel type

### Functional requirements
| ID | Requirement |
|---|---|
| P1 | Download the files for a given date range idempotently: re-running never duplicates rows |
| P2 | Parse AEMO's multi-table CSV format into typed tables |
| P3 | Validate every table against a schema: types, required columns, allowed ranges, unique keys |
| P4 | Align all series to the 5-minute dispatch interval (AEST, market time) and flag gaps |
| P5 | Quarantine rows that fail validation into a rejects table that records the reason. Never drop them silently |
| P6 | Retry network failures with backoff, log every run (structured logs), and resume from the last good file |
| P7 | Write tables to DuckDB, plus Parquet/CSV exports shaped for Power BI (star schema: one fact table per dataset, date and unit dimensions) |
| P8 | Record a run manifest for each run: source URLs, file hashes, row counts, rejects, code version |

### Acceptance criteria
- AC-P1: Loading the same week twice gives identical row counts and table hashes.
- AC-P2: A corrupted or truncated file is logged and quarantined, and the run carries on with the remaining files.
- AC-P3: In a full week of data, SA1 has 2,016 dispatch intervals, with gaps reported if any are missing.
- AC-P4: Reconciliation check: SA1 demand ≈ SA unit SCADA output plus net interconnector import, within a documented tolerance. Losses and non-scheduled generation explain the remainder. Any interval outside tolerance is flagged.
- AC-P5: Unit test coverage ≥ 85% on the parsing and validation modules. CI passes on every push.
- AC-P6: The Power BI exports load without any transformation steps (documented in `docs/powerbi.md`).

## 3b. Investigations (identify, investigate and respond to issues)

Three short investigations on the real Stage 1 data, each one using data science, maths or statistics to answer an engineering-style question. Each one is a script plus a written report in `docs/investigations/`, structured as question, data, method, finding, limitations and recommended response.

| ID | Question | Methods |
|---|---|---|
| I1 | **Which network constraints bind most often in SA, and what drives them?** Rank binding constraints by frequency and marginal value, and test how they relate to wind output, rooftop PV, demand and interconnector flow | Aggregation, logistic regression / gradient boosting with SHAP or partial dependence, confidence intervals |
| I2 | **How often is the Heywood interconnector at its limit, and under what conditions?** Characterise the periods at or near the limit and their seasonal and time-of-day pattern | Time-series decomposition, hypothesis tests, survival-style run-length analysis |
| I3 | **Is the SCADA data trustworthy?** Detect stuck (flatlined) readings, spikes, and units reporting output while offline | Robust z-scores, rolling statistics, change-point detection. Output: an issues register with a suggested fix or escalation for each issue |

### Acceptance criteria
- AC-I1: Every number in a report is regenerated by a script from a pinned data snapshot (no hand-edited figures).
- AC-I2: Each report states the limitations of the evidence: correlation is not causation, and public data is not network-internal data.
- AC-I3: Each report ends with a concrete recommended response, such as a monitoring rule, a data-quality check added to the pipeline, or a study to run in Stage 2.
- AC-I4: At least one finding feeds back into the code. For example, an I3 data issue becomes a new validation rule in P3.

## 4. Stage 2: Reproducible contingency studies

### Approach
- Use a published pandapower test network. A candidate is a CIGRE or IEEE test case, chosen during build and documented with its source.
- Map SA operating snapshots onto the network: scale load to SA1 demand, set generator dispatch by fuel-type share, and set the boundary injection to the interconnector flow.
- Snapshot selection rules: annual peak demand, minimum operational demand (high rooftop PV), maximum import and maximum export.

### Functional requirements
| ID | Requirement |
|---|---|
| S1 | Define each study in a YAML file: network, snapshot rule, contingency list, limits |
| S2 | Run base case and N-1 (each line and transformer out in turn) AC load flow |
| S3 | Check results against limits: thermal loading > 100%, voltage outside 0.95–1.05 pu, non-convergence |
| S4 | Validate inputs before solving: power balance, no isolated buses, limits present |
| S5 | Produce a study report (HTML or Markdown) and result tables for Power BI |
| S6 | Make every study reproducible: same YAML + same data snapshot + same code version gives identical results |

### Acceptance criteria
- AC-S1: The base case on the unmodified test network matches pandapower's reference results.
- AC-S2: Rerunning a study from its manifest gives byte-identical result tables.
- AC-S3: A non-converging contingency is reported as such and does not stop the run.
- AC-S4: Invalid study inputs (such as a missing limit or an unknown snapshot rule) fail fast, with a clear error message.

| Testing and validation of analytical outputs | pytest unit tests, reconciliation checks, reference-case checks (AC-P4, AC-S1) |
| Requirements and acceptance criteria | This document |
| Power BI multi-source dashboards | Star-schema exports from both stages |

| Time-series handling | Timestamp alignment, resampling and gap detection (P4) |

## 6. Tech stack
Python 3.11, pandas, pandera (schemas), DuckDB, pandapower, pytest, ruff, GitHub Actions. Power BI for the dashboard. Power BI Desktop needs Windows, so the exports are kept tool-agnostic.
